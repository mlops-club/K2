K2 Distributed Runtime

Split the K2 daemon into a controller and agent hosts so permanent agents can run on a laptop, one VM, a fixed set of VMs or a Kubernetes cluster, with every feature working the way it does today. Each stage ships with proof that runs, not a promise.

1 · Problem and goals

K2 assumes one machine. Its agents don't have to.

Today one k2-daemon process owns everything: the SQLite database behind one mutex, a singleton lock file, every agent's PTY, the scheduler, the tunnel and Caddy. A root helper edits the host through systemd. Agents run as the daemon's own user and the hook owner check walks /proc on the same kernel. That design is why K2 is light, and it is also why K2 cannot spread across machines.

Two facts make distribution practical. First, K2 already treats agent processes as disposable: on restart it kills them and relaunches with claude --resume, and agents untouched for 24 hours have no process at all. A permanent agent in K2 is a durable identity, a durable home directory and a resumable conversation, not a process that never dies. Second, k2-node already is a remote worker built the right way: it dials out, signs every frame and syncs code with git. It runs jobs, not agents.

Goals

  • One design that runs as a single laptop or VM, a fixed fleet of VMs, or on Kubernetes. Same binaries, different wiring.
  • Every feature that works today keeps working in every mode: Postgres, Apps, mail, Sew, Connect, vault, heartbeats, messaging, federation.
  • Single-machine mode stays exactly as light as it is now. 500 mostly-sleeping agents on one node stays normal.
  • Agents survive controller restarts. A daemon upgrade stops killing agent sessions.
  • Kubernetes is optional and native when used: StatefulSets, Gateway API, the Zalando postgres-operator, node autoscaling.
  • Docker Compose is a first-class mode: one file shows the whole end-state architecture on one machine.
  • Each stage is proven with runnable evidence the original authors can rerun with one command.

Non-goals for this PRD

  • Live migration of a running CLI process between machines. Agents move by stopping and resuming, as they restart today.
  • Controller high availability. One controller replica plus disposable hosts covers the need; HA is a later, separate decision.
  • Multi-tenant hosting for K2 Connect. The first Kubernetes target is self-hosted, for example a home k3s cluster.
  • Choosing pod-per-agent now. Section 5 gathers the evidence; the decision is made at gate G4 with real numbers.
Decisions so far · Kubernetes users are self-hosters first (an owner's own k3s cluster). Postgres, Apps, mail and every other root-helper feature must work there. Pod granularity is on hold pending evidence. Laptops: recommendation in section 7.
2 · The design, level by level

See the runtime one level of abstraction at a time

Each level shows about five things and how they connect, then the main flows at that level as sequence diagrams you can step through. Use i on a box for what it holds, what it does and where it lives in today's code. Use Look inside to go down a level.

The sequence diagrams are not just illustrations. Section 3 turns each one into an expected trace that the conformance runner checks against the real system.

The whole change is one split

K2 today is a client talking to one daemon, and that daemon also runs every agent's terminal and CLI. The proposal cuts the daemon in two. The controller is today's daemon minus the agent processes; there is exactly one. An agent host is the code that runs agent terminals and CLIs, pulled out so it can sit on another machine. On a single laptop or VM the host stays inside the same process, so nothing changes there.

3 · How we prove it

Every stage proves itself on five topologies

Nobody gets a change this size right in one pass, so the plan is built around evidence. Each stage ends at a gate. A gate passes only when a single command, scripts/lab/prove.sh <gate>, brings up the topologies, runs the scenarios and writes an evidence bundle anyone can open. The authors don't have to trust a summary; they rerun the command.

  • 1. Parity firstSingle-machine mode must stay identical. Every gate reruns the existing suites unchanged: scripts/test-gate-linux.sh, tests/cli/* (158 scripts), the must-not-break contract and the behavior tiers.
  • 2. One scenario suite, many topologiesThe same scenarios run against solo, container, fleet, Kubernetes host pods and Kubernetes per-agent sandboxes. A scenario that only passes on one topology is a failure.
  • 3. A fake agent that behaves like a real onek2-fake-agent grows from today's AgentShim (exec cat). It takes pasted input, runs a timed "turn", writes a transcript JSONL and a memory file, fires SessionStart, UserPromptSubmit and Stop hooks, and resumes with --resume <id>. No API keys, so 500 of them fit in a lab.
  • 4. The diagrams are the testsController and hosts emit trace events tagged with agent and message ids. Each sequence diagram in this page is stored as data in docs/prd/flows/*.json. The runner checks that the observed events contain the diagram's steps in order, and the report draws observed next to expected.
  • 5. Chaos with a fixed seed--chaos kills a random CLI, host or controller during scenarios S3 to S10. The seed is in the report, so any failure replays exactly.
  • 6. Real CLIs at the end of each gateAfter the fake-agent run, a short smoke test with real claude and codex sessions confirms resume and hooks with the real tools. It needs keys, so it runs on the owner's machine or cluster.

Invariants every run checks

I1An agent has at most one live placement. Each placement carries an epoch; a host with a stale epoch is refused.
I2Every message reaches a final state: delivered, or failed loudly. None vanish.
I3A resumed agent keeps its provider session id and its memory files byte for byte.
I4An agent's home is written by one host at a time.
I5Solo mode output matches the pre-change baseline on every existing suite.

4 · Stages and gates

Six stages, each ending in something you can watch work

Stages are ordered so that each one is useful alone, and so that Kubernetes arrives last, on top of a design already proven on plain machines.

P0 → G0K2 in a containerToday's architecture, in one pod.

Build

  • K2_HOME honoured everywhere: about 300 ~/.k2 and home_dir() call sites move behind k2_client::paths, with a ratchet test like the existing env-mutation ratchet.
  • Capability detection at boot: each root-helper feature reports host-native, delegated or off.
  • OCI image with binaries under /usr/bin, so install_kind="package" turns self-update off. Same opt-out for root helper, app engine and node.
  • Kubernetes manifests: one StatefulSet with a PVC, Postgres through the Zalando postgres-operator or an external URL. A Helm chart wraps the same manifests later.

Proof

  • All existing suites green inside the container, as root and as a random UID.
  • must-not-break passes against the pod, including the Postgres checks.
  • S1, S2, S7, S12 on solo and container.
  • Demo: helm install on kind, sign in, run an agent.
prove.sh G0 --topology container

Build

  • An AgentHost interface inside the daemon: spawn, attach, stream, resize, inject, kill, hook events, read and write the home.
  • The in-process implementation wraps today's DaemonPtySession path.
  • Trace events at every hop; flows stored as JSON; k2-fake-agent.

  • I5: every existing suite matches the pre-refactor baseline.
  • Trace diff passes for spawn, hook event and CLI-crash flows on solo.

Build

  • Hosts keep agents running while the controller restarts, then replay from ring offsets.

  • S1 to S9 on fleet and solo, chaos on, all invariants.

5 · Density: pods vs processes

Containers cost about 3% more memory. The real costs are elsewhere.

The worry: 500 agents run on one node today, and wrapping each in a pod could throw that away. We measured on the lab cluster rather than guessed. Each kind node is a Docker container, so absolute numbers on a real k3s node will differ, but the ratios hold.

What the numbers say
  • The memory fear does not hold. The CLI dominates: about 400 MB per awake agent against 12 MiB of pod overhead.
  • The CPU and pod-count fears partly hold. Kubelet does real work per pod, and 500 awake agents as pods needs a raised pod limit or more nodes.
  • The bigger costs of pod-per-agent are volumes per agent, slower wake, and duplicating the shared home that makes K2 cheap.
  • Hardened runtimes are not free: gVisor adds about 47 MB per sandbox and makes git roughly 3× slower in one third-party benchmark; Kata adds 120–300 MB per pod.
Working recommendation, decided at G4
  • Default to host pods: a few pods each running many agents. Kubernetes then looks like a fleet of VMs, and K2's density and semantics stay as they are.
  • Offer pod-per-agent on agent-sandbox as an opt-in isolation tier for untrusted or shared clusters.
  • Both tiers sit behind the same AgentHost interface, so this choice never leaks into the rest of K2.
  • Precedent: Gitpod left Kubernetes in 2024 because stateful, spiky dev environments fit pods poorly; Coder runs several agents per workspace.
6 · When things die

Pods die. Agents should only notice a pause.

An agent's identity, relationships and learning do not live in its process. Its AGENT.md, skills, inbox and MEMORY.md live in its home, its conversation lives in the provider's transcript, and its connections, heartbeats and pins live in the controller's database. So the question for each failure is what was in flight, and whether it is lost silently. The distributed design must lose no more than today and, for controller restarts, much less.

Seen live in the lab, and what it means for a k3s cluster
  • Draining a node left a Sandbox pod Pending for good: its volume used local-path storage, which pins it to one node. k3s uses local-path by default.
  • So on k3s, an agent can only move between nodes with replicated storage (for example Longhorn) or with K2's own home sync from stage P3. Either is fine; the chart has to choose one explicitly.
  • agent-sandbox reported Ready during a resume while the old pod was still terminating. K2 must gate on its own host handshake, never on the custom resource's status.
7 · Laptops

Recommendation: laptops enroll as hosts

Mature systems with machines that come and go all use the same shape: the machine dials out to one controller with a revocable credential and keeps its own data. GitHub Actions runners long-poll over 443. Buildkite marks a silent agent lost after 3 minutes. Coder's external workspaces attach machines it doesn't control and never start or stop them. None use peer-to-peer federation for one owner's machines. K2 already has both pieces: k2-node enrollment, and federation between independently owned daemons.

OptionHow it worksGood forCosts
Laptop enrolls as a host recommendedThe laptop runs k2-host and dials out to the team's or the owner's controller. Its agents are pinned to it.One owner or team; one place to see every agent; messages between laptop and cloud agents.New agents need the controller reachable. Running agents keep working offline.
Laptop stays soloToday's mode: the laptop runs its own controller and host.People who want nothing remote.Cloud agents are a separate K2.
Federation between controllersTwo independent K2s exchange signed agent signals (exists today, behind K2_FEDERATION).Crossing ownership lines: personal and work, two companies.Separate identities and databases; not a fleet.
  • Away is not deadA silent laptop host becomes "away" after 90 seconds. Its agents show as paused and are never placed elsewhere, because their repo and memory live on the laptop.
  • Identity is a key, not an addressHosts are known by their enrolled key, so a new IP after wake changes nothing.
  • Secrets stay where they are usedThe laptop's own provider logins and SSH keys stay on the laptop. The controller sends commands, not credentials.
  • Messages waitThe outbox holds messages for an away host (default 7 days) and drains them on reconnect.
  • Offline still works locallyIf the laptop can't reach the controller, its agents keep running and the local app attaches straight to the laptop's own host: live terminals, typing, scrollback (FR11). New agents, messages to other machines and heartbeats wait as "pending" until the controller is back.

8b · Decisions and end state

Decided, and written down before the code

ADR-0001 · Agent isolation inside host pods

Decision: agents in a host pod share one UID with no added capabilities, as every K2 install does today. Per-agent UIDs (root plus SETUID, SETGID, CHOWN, reusing cell_uid_pool) are an opt-in profile. One pod per agent on agent-sandbox is the strong-isolation tier.

Tradeoff: the default passes Pod Security "restricted" and costs nothing per agent, but an agent can read its neighbours' homes and the host's link key. The controller limits a stolen key to agents already placed on that host.

docs/adr/adr-0001-agent-isolation-inside-host-pods.md

ADR-0002 · One controller, no high availability

Decision: exactly one controller in every mode, on SQLite. Postgres stays a capability for Apps, not the controller's store.

Tradeoff: while it is down, awake agents keep working and the local app can attach directly (FR11), but spawns, wakes, heartbeats and cross-host messages wait. HA would need a Postgres store, leader election and shared in-memory state. Revisit if the G5 soak shows outages hurting.

docs/adr/adr-0002-single-controller.md

9 · Requirements

Requirements

Functional

  1. FR1 The controller places, starts, attaches, sleeps, wakes and moves agents through one AgentHost interface with an in-process and a remote implementation.
  2. FR2 Hosts dial out over a signed WebSocket, enroll with a one-time code and a confirmation string, and are known by key.
  3. FR3 Hook owner checks run on the host; the controller accepts only host-attested events.
  4. FR4 Messages between agents use a durable outbox with ids, at-least-once delivery and receiver dedupe.
  5. FR5 Agents keep running through controller restarts; clients replay output from ring offsets.
  6. FR6 An agent's home (workspace, .k2/, provider memory and transcripts) can be exported, moved and restored.
  7. FR7 Provisioners: Local, Static (enrolled VMs and laptops), Kubernetes host pods, Kubernetes Sandbox.
  8. FR8 Agents can be marked pinned or portable. Laptop agents are pinned.
  9. FR9 Every root-helper feature has a capability driver per mode, as in section 8.
  10. FR10 Declarative installs: deploy/compose/compose.yaml for Docker Compose and deploy/kubernetes for k3s and managed clusters, later wrapped in a Helm chart.
  11. FR11 When the controller is unreachable, the local app attaches directly to the agents on its own machine's host (K2_HOST_LOCAL_ATTACH): live terminals, typing, scrollback. Actions that need the controller (new agents, messages to other hosts, heartbeats) queue and show as pending until it returns.

Non-functional

  1. NFR1 Solo mode: no regression on any existing suite; idle RSS and spawn latency within 5% of baseline.
  2. NFR2 A sleeping agent costs no process on any topology.
  3. NFR3 Wake to ready, p95: 10 s on a running host, 30 s when a pod must be scheduled. Today's injection waits up to 20 s for CLI readiness.
  4. NFR4 No silent message loss under chaos (invariant I2).
  5. NFR5 Host pods: 100 awake agents per host pod on a 64 GB node without node pressure.
  6. NFR6 Everything works without Kubernetes and without containers.
  7. NFR7 No inbound ports on hosts; laptops work behind NAT.
  8. NFR8 Each gate is reproducible from a clean checkout with one command.
